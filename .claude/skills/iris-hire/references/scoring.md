# 匹配度打分模型（scoring）

> 配套岗位标准库（默认 `data/hiring/job-catalog.md`，本地私有、不入仓）使用。本文件定义「怎么算分、怎么定档、怎么报置信度」，不含岗位标准本身。

## 一、总分算法

```
总分 = Σ(维度权重ᵢ × 维度得分ᵢ) / 5
```

- 维度得分 `0–5`，权重合计 `100` → 总分区间 `0–100`
- **gate 不参与加权**：任一 gate 不满足 → 结论直接标「不推荐」，但仍输出总分与各维度分供参考

## 二、维度得分锚点（0–5，标准 track 通用）

| 分 | 含义 | 判定要点 |
|:--:|------|------|
| **5** | 显著超出 | 能定义标准、带人、或把方法跨域迁移；有可复用的方法论沉淀 |
| **4** | 超出要求 | 能优化方法本身、覆盖边界情况、有可量化收益 |
| **3** | 达标 | 能独立完成本岗典型任务，不需指导 |
| **2** | 部分达标 | 有独立产出但范围受限，或需他人指导才能完整闭环 |
| **1** | 相关但浅 | 仅接触过，无独立产出 |
| **0** | 无证据 | 简历与面试均无相关信息 |
| **n/a** | 无法判断 | 简历信息不足；**记 n/a 而非 0**，并转为面试待验证假设 |

轻量 track（标注岗）与管理岗沿用同一 0–5 标尺，锚点含义见岗位库对应条目。

## 三、三条打分纪律

1. **每项得分必须挂证据**。证据 = 简历原句 / 项目描述 / 面试回答。无证据按 0 记，不按「大概他会」给分。
2. **n/a ≠ 0**。信息缺失是「不知道」，不是「不具备」。n/a 的维度按剩余权重归一化后计入总分，同时拉低置信度。
3. **同分不同义要标注**。若两岗位总分接近（差 < 5 分），在结论中说明「差异来自哪个维度」，不靠总分硬排。

## 四、职级档推断

打分前必须先定档——同一岗位 L1 与 L3 的标准不同，用错档会造成系统性误判。

| 档 | 对应职级 | 经验区间（仅参考） | 特征 |
|:--:|:--:|:--:|------|
| **L1** | 3–4 级 | 0–3 年 / 校招 | 在指导下完成模块，尚未独立负责方向 |
| **L2** | 5–6 级 | 3–8 年 | 独立负责一个子系统或一个技术方向 |
| **L3** | 7 级以上 | 8 年以上 | 技术负责人 / 架构角色，或能定义团队标准 |

**判定优先级：责任边界 > 工作年限。** 年限只作交叉验证——有人 5 年仍在做模块实现（L1 边界），有人 3 年已独立带方向（L2 边界）。

若候选人所处档位落在目标岗位职级带之外（如岗位带 4–6，候选人为 L3），在输出中提示「职级带可能不匹配（岗位 X–Y，候选人推算 Lz）」，但仍照常打分。

## 五、AI 应用能力（D5）三档锚点

这是知识库中唯一一份显式能力标准，按职级通道分层，**独立于专业技能评估，是必要项而非充分项**。

**算法通道**（算法族 5 岗适用）

| 档 | 锚点 |
|:--:|------|
| L1 | 熟练使用主流 AI 编程工具与大模型 API；借助 AI 完成算法调试、调参、训练、数据处理、Demo 搭建；能调用 API 完成基础 NLP 任务或基于规则搭简单 Agent |
| L2 | 能把 LLM 能力融入算法方案并甄别其输出合理性；能调度 Agent 完成完整数据任务；能封装可复用 Skill；具备 Prompt 与流程调优能力 |
| L3 | 多模型协同（LLM + 深度学习）复杂系统设计或多智能体架构；能用蒸馏 / 多模态对齐 / AI 工程降本；能把业务需求转化为 AI 场景并拿到可量化收益 |

**工程通道**（其余技术岗适用）

| 档 | 锚点 |
|:--:|------|
| L1 | 了解大模型 / Prompt / RAG 概念与边界；在指导下用 AI 做 SQL、注释、报错解读、文档整理；对 AI 输出有基本校验意识 |
| L2 | 把 AI 用到建模 / ETL / SQL 优化 / 校验 / 排查 / 口径整理；为不同任务设计有效 Prompt 并沉淀模板；能有效验证与修正 AI 输出 |
| L3 | 识别并推动 AI+Data 高价值场景落地（智能问数、异常归因、指标解读、治理辅助）；建设可复用 AI 能力载体；建立效果 / 成本 / 风险 / 安全使用规范；形成推广机制与标杆 |

管理岗按**所带团队的通道**取锚点（带算法团队取算法通道，其余取工程通道）。

## 六、档位换算

| 总分 | 档位 | 后续建议 |
|:--:|------|------|
| **≥ 80** | 强匹配 | 建议直接进面试，可上探一级职级 |
| **65–79** | 匹配 | 正常面试，重点验证 n/a 维度 |
| **50–64** | 基本匹配 | 需针对性加面或明确降级录用 |
| **< 50** | 不匹配 | 不建议推进（除非岗位紧急且 gate 全过） |
| **gate 未过** | 不推荐 | 不论分数，不作为候选 |

## 七、置信度

| 置信度 | 条件 |
|:--:|------|
| **高** | 有量化结果 + 责任边界清晰 + 技术栈明确，缺项 ≤ 1 个维度 |
| **中** | 上述缺 1 项，或缺 2–3 个维度信息 |
| **低** | 缺 2 项以上，或简历无项目描述 / 无技术栈 / 仅一页无细节 |

置信度必须输出。**低置信度的匹配度不应作为筛选依据**，应直接进面试或要求补充材料。

## 八、两种匹配入口的规则

### 模式 A · 自动匹配（默认）

1. 对岗位库中的全部岗位过 gate
2. 对 gate 全过的岗位打分
3. 按总分降序排名，输出 Top 3 + 「其余岗位最高分」
4. 若 Top 1 与 Top 2 差 < 5 分 → 明确写出差异维度，不强行给出唯一答案

### 模式 B · 手动指定

用户直接说岗位名时（如「按大模型算法岗评」「看看他适不适合测试」）：

1. 用岗位库的**别名**匹配岗位 id；匹配不到 → 列出相近岗位请用户确认，**不得猜**
2. 只评该岗位，输出完整维度分 + gate 结论 + 档位
3. **错配提示**：若该岗位得分比自动匹配的最高分低 **≥ 15 分**，追加一行提示「候选人在 `<某岗位>` 得分更高（`<分数>`），是否改判」——仅提示，不改结论
4. 用户坚持原岗位 → 按原岗位出面试方案，并在结论中记录「用户指定，已提示错配风险」

### 两模式共用

- 手动模式的输出**不省略** gate 与置信度
- 任何模式下，简历信息不足以判断某维度时记 `n/a`，并把这些维度转化为面试的待验证假设

## 十、一致性自检

同一份简历重复评分时：

- 总分差异 > 10 分 → 存在口径漂移，复核锚点使用是否一致
- 同一维度两次给分差 ≥ 2 → 该维度证据不足，应记 `n/a` 而非强行给分
- 建议在输出中保留每个维度的证据摘要，便于事后复核
